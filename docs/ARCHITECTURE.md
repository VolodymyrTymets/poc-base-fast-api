### Where data truth lives
Only the seed runner, `AccountRoleService.add_account_to_role` (task 5.2) and `AccountService.create_customer` (task 5.3, called by `POST /auth/otp/request`) and `create_password_account` (task 5.3, called by `POST /auth/sign-up` through `PasswordAuthService.sign_up`, task 7.3: the password is an Argon2id hash in `AccountIdentity.hash` and `salt` stays null, the answer ADR-0028 left to 7.3), `OtpService.issue` / `OtpService.spend` and `TokenService.issue`, `TokenService.rotate` and `TokenService.revoke` (tasks 7.1, 7.2 and 7.4; the last two through `POST /auth/refresh` and `/sign-out`: the OTP columns and the refresh hash of `AccountIdentity` and `AccountProfile.isPhoneVerified`, through `POST /auth/otp/request` and `/verify`), `PasswordAuthService.issue_reset_token` and `reset` (task 7.6, through `POST /auth/password/restore` and `/reset`: restore writes `resetTokenHash` and `resetTokenExpiresAt`, creating the `AccountIdentity` row of an OTP-only account; reset replaces `hash` and clears the same six columns as a change, conditional on the token still being there and unexpired), `PasswordAuthService.change` (task 7.5, through `POST /auth/password/change`: the password `hash` replaced and, in the same UPDATE conditional on the hash that was checked, `refreshToken`, `resetTokenHash`, `resetTokenExpiresAt`, `otpHash`, `otpSalt` and `otpExpiresAt` cleared), `AccountProfileService.update` (task 5.4, through `PATCH /accounts/{accountId}/profile`) and the development seed items of task 5.5 (the admin and three customers) write to a database so far, and the schema has a home: revision `0001_init` (task 2.4) builds the tables below, the two enum
types and the `postgis` extension on an empty database, and `alembic check` fails when the models and the revisions drift apart. The account, file, notification and
system models are mapped (tasks 2.2, 2.3 and 5.1) and importing `app.models` registers ten tables on `Base.metadata`: `Account`, `AccountRole`,
`AccountOnRole`, `AccountIdentity`, `AccountProfile`, `File`, `Notification`, `NotificationRecipient`, `DeletedHistory` and `SeedHistory`, plus the
`AccountRoleType` and `FileType` enums. `FileType` is tied to the metadata directly because no column uses it; without that `create_all` and Alembic
would never emit the Postgres type. `File.content` is `bytea` (ADR-0009), plain and not deferred.
`DeletedHistory` has no `deleted` column, as in the Node schema, and nothing writes to it yet. `SeedHistory` (revision `0002_seed_history`, task 5.1: `id`, `name` unique, `successful`, `result`, `createdAt`) is this base's own table, not Node's `Migration`: one row per seed item, updated in place when a failed item is retried, no `deleted` column. The Node `Migration` table is not mapped: Alembic's `alembic_version` records applied revisions ([ADR-0018](decisions/ADR-0018-drop-migration-table.md)). Names, column types, primary keys, foreign-key actions and
indexes follow the Prisma DDL, except that `AccountProfile` has no `SSN` or `is18YearOld` column ([ADR-0015](decisions/ADR-0015-drop-ssn-and-is18yearold.md)); every unique is a unique index (as Prisma emits it) and `Account_createdAt_idx` is `DESC`. Attributes
are snake_case over the quoted column names (`created_at` for `"createdAt"`, `date_of_birth` for the Node column `"dataOfBirth"`),
relationships are snake_case, plural for a collection, not Prisma's PascalCase ([ADR-0016](decisions/ADR-0016-snake-case-relationship-names.md); `Account.identity`, `Account.account_on_roles`, ...). `AccountProfile.avatarId` has its
foreign key to `File` (`AccountProfile.avatar`, `Account.files`, `Account.notification_recipients`). The data layer plumbing is built: with
`DATABASE_URL` set, `create_app` builds one SQLAlchemy async engine (asyncpg, session time zone UTC) and the lifespan disposes it;
`get_session` gives each request its own `AsyncSession`, which never commits by itself. Without `DATABASE_URL` the app boots and
only a route that needs a session fails. With `DATABASE_URL` set, the lifespan runs the seed items (the roles, today) before the app serves, each in its own transaction under an advisory lock; a failing item is rolled back and recorded in `SeedHistory`, and the boot stops with `SeedError` (a decision of POC-5.1: the Node base logged the failure and served on). The same runner is `python -m app.seeds`. The engine hides statement parameters from error text (`hide_parameters`, rules D8 and P4). No cache is wired. The queue is: `create_app` builds an `ArqQueueClient` into `app.state.queue` (its Redis pool opens on the first enqueue, so the app boots with no Redis; an enqueue with Redis down raises after one connection attempt), the lifespan closes it, and `get_queue` in `dependencies.py` hands it to a route or service. Job payloads cross Redis as JSON, never pickle.

### Boundaries and contracts
The REST contract is written down in [docs/api/ENDPOINTS.md](api/ENDPOINTS.md). Twelve routes exist, `GET /api/v1/health`, `POST /api/v1/auth/otp/request` (task 7.1: no auth; issues a 6-digit code for a phone number, creating a customer account for an unknown one, stored as an Argon2id hash valid 2 minutes; the SMS job is queued after the commit; `code` is in the body only for `local`, `development` and `test`; [ADR-0028](decisions/ADR-0028-argon2-hashing-pwdlib.md)), `PATCH /api/v1/accounts/{accountId}/profile` (task 5.4: all three layers of rule P7, the ownership check in `AccountProfileService`; the first route that uses `require_roles`) and `POST /api/v1/auth/otp/verify` (task 7.2: no auth; exchanges a code for `{accessToken, refreshToken}`, one 401 `INVALID_CREDENTIALS` for every failure, the code single-use, the refresh token stored as sha256, [ADR-0008](decisions/ADR-0008-auth-tokens-refresh-hash-and-transport.md)), `POST /api/v1/auth/sign-up` (task 7.3: no auth; 201 `{accessToken, refreshToken}`, a customer account with the email lowercased and an Argon2id password; an email on any profile, a soft-deleted one included, is 409 `EMAIL_ALREADY_REGISTERED`, also when the unique index decides a race), `POST /api/v1/auth/sign-in` (task 7.3: no auth; 200 with a new pair that replaces the stored refresh hash; an unknown email, a wrong password, an OTP-only account and a soft-deleted account, profile or identity are one 401 `INVALID_CREDENTIALS`, each with one Argon2 check), `POST /api/v1/auth/refresh` (task 7.4: refresh token in `x-refresh-token`, 200 with a new pair that replaces the stored hash; every failure, the replayed token and a soft-deleted account included, is 401 `UNAUTHORIZED`), `POST /api/v1/auth/sign-out` (task 7.4: Bearer, 204 with no body, clears the refresh hash and the sign-in code, idempotent; the access token stays valid until it expires), `POST /api/v1/auth/password/change` (task 7.5: Bearer, 204 with no body; a wrong current password, an account with no password and a soft-deleted account are one 401 `INVALID_CREDENTIALS`; the refresh token, reset token and sign-in code of the old password are cleared), `POST /api/v1/auth/password/restore` (task 7.6: no auth; 200 `{success: true}` for every well-formed email, never the token; a registered account gets a sha256-stored token valid 30 minutes and an email job queued after the commit; known and unknown emails differ only in response time) and `POST /api/v1/auth/password/reset` (task 7.6: no auth; 204 with no body; an unknown, used, expired or soft-deleted-account token is one 400 `INVALID_RESET_TOKEN`; no Argon2 work for a garbage token) and `GET /api/v1/account` (task 5.3: the caller's account and live profile; a token whose account is missing or soft-deleted is 401, [ADR-0022](decisions/ADR-0022-self-scoped-routes-need-authentication-only.md)); the six feature routers (`app/routers/<module>.py`, each an `APIRouter` with its own tag) are included under `/api/v1`, and all but `account`, `account_profile` and `auth` (nine routes so far) are still empty, and `/docs` lists their tags; CORS allows the origins in `CORS_ORIGINS`. Every error uses one body, `{"error": {"code", "message", "details"}}`, built in `app/core/errors.py` and listed in [docs/api/ERRORS.md](api/ERRORS.md); the OpenAPI contract documents it for 422 and 500. A request body over `MAX_REQUEST_BODY_BYTES` gets 413 before routing (the body limit sits inside CORS, so the 413 carries CORS headers). Logs are JSON on stdout with tokens, passwords, DOB and phone numbers redacted; Sentry is off for `local` and without `SENTRY_DSN`. SIGTERM stops the server after `SHUTDOWN_TIMEOUT_SECONDS` at most. The one generated file is the root `openapi.json`, written by `uv run python -m app.cli --export-openapi` and checked by `tests/unit/test_openapi_stale.py`; a test also fails when a route has no response model or a response model holds an ORM class.

## Decided (ADR-0003 to ADR-0032, built by the scope-doc tasks)
Supersession applies to this repo only; the Node repo's ADRs stay in force there.

- REST with FastAPI under `/api/v1`, Pydantic models, error body `{"error": {...}}`, contract exported to a root `openapi.json`
  with a stale-spec test ([ADR-0003](decisions/ADR-0003-rest-api-fastapi-openapi.md)).
- SQLAlchemy 2 async + asyncpg + Alembic on Postgres/PostGIS, Prisma table and column names as a naming target, not diffed (ADR-0019)
  ([ADR-0004](decisions/ADR-0004-data-layer-sqlalchemy-alembic.md)).
- Alembic in `migrations/` with `alembic.ini` at the repo root, the URL from `Settings`, hand-written frozen revisions that import nothing from `app`,
  `alembic check` with type and default comparison on; it extends ADR-0011 with the import rule for `env.py`
  ([ADR-0017](decisions/ADR-0017-alembic-migrations-directory.md)).
- No `Migration` table: Alembic's `alembic_version` records applied revisions; a third difference from the Node schema next to ADR-0015's two columns
  ([ADR-0018](decisions/ADR-0018-drop-migration-table.md)).
- arq worker on Redis, a separate process; retries by `Retry(defer=...)`
  ([ADR-0005](decisions/ADR-0005-job-queue-arq.md)); the entrypoint is `app/worker.py` and the queue seam is `app/core/queue.py`
  ([ADR-0024](decisions/ADR-0024-worker-entrypoint-module.md)).
- Tests on a real PostGIS Postgres through testcontainers, one template database per run; built in task 3.1 and in use, the seeds are part of the
  template since task 5.1 ([ADR-0006](decisions/ADR-0006-test-database-testcontainers.md)).
- ruff, mypy strict, pytest, installed in task 1.4 and in use ([ADR-0007](decisions/ADR-0007-quality-tooling-ruff-mypy-pytest.md)).
- Opt-in column mixins (`id` as `text`, `createdAt`/`updatedAt` as UTC `timestamp(3)`, `deleted`) and Prisma-shaped constraint names, built in
  task 2.1; it supersedes one bullet of ADR-0004 ([ADR-0014](decisions/ADR-0014-opt-in-column-mixins.md)).
- Relationship attributes follow SQLAlchemy convention (snake_case, plural collections), not the Node base's PascalCase
  ([ADR-0016](decisions/ADR-0016-snake-case-relationship-names.md)).
- `AccountProfile` omits the Node columns `SSN` and `is18YearOld`; with the dropped `Migration` table and the added `SeedHistory` table (revision `0002_seed_history`, task 5.1) these are the known differences from the Node schema (ADR-0019)
  ([ADR-0015](decisions/ADR-0015-drop-ssn-and-is18yearold.md)).
- Schema parity with the Node base is a naming convention, not proven by a `pg_dump` diff; task 2.5 is a smoke run of `alembic upgrade head`, `alembic check` and the app
  ([ADR-0019](decisions/ADR-0019-schema-parity-not-diffed.md)).
- Sentry as the error sink, off for `local` and without a DSN, with whole-event redaction ([ADR-0013](decisions/ADR-0013-sentry-error-reporting.md)).
- `app/cli.py` holds the project commands that need the whole app, starting with the `openapi.json` export; `main.py` stays the app only
  ([ADR-0020](decisions/ADR-0020-cli-module.md)).
- A self-scoped route (the record comes from the token) needs authentication only ([ADR-0022](decisions/ADR-0022-self-scoped-routes-need-authentication-only.md)).
- `seeds` may import `schemas`, so seed data goes through the request models ([ADR-0023](decisions/ADR-0023-seeds-may-import-schemas.md)).
- A service is a class over an `AsyncSession`; it flushes and never commits, the caller owns the transaction
  ([ADR-0021](decisions/ADR-0021-service-shape-and-transactions.md)).
- One `Depends` provider per service in `app/dependencies.py`; a route takes it and owns the commit, a test swaps it with `dependency_overrides`
  ([ADR-0025](decisions/ADR-0025-service-providers.md)).
- The password-reset job logs the recipient and token in `local`, `development` and `test` only, an exception to rules D8 and P4 for that job
  ([ADR-0026](decisions/ADR-0026-worker-logs-reset-token-in-dev-envs.md)).
- A service may be built from other services and core seams instead of a session; it never commits, and a database error from a service it uses propagates
  ([ADR-0027](decisions/ADR-0027-service-built-from-services.md)).
- Sign-in codes and passwords are hashed with Argon2id through `pwdlib[argon2]`, one seam in `app/core/hashing.py`, OWASP's minimum cost (19 MiB, 2 iterations, 1 lane); it supersedes the password bullet of ADR-0008
  ([ADR-0028](decisions/ADR-0028-argon2-hashing-pwdlib.md)).
- One image, targets `development` and `worker`; the entrypoint owns the wait, the migration and the seeds, and the worker never migrates; `HOST` (default `127.0.0.1`, `0.0.0.0` in the image) is the bind address; `scripts/` is the new tooling directory
  ([ADR-0030](decisions/ADR-0030-container-image.md)).
- CI: one workflow with three parallel jobs (static, tests, e2e), pinned uv, real Postgres through testcontainers, no secret
  ([ADR-0032](decisions/ADR-0032-ci-workflow.md)).
- Compose stack of four services (no web); containers read `.env.development`, the root `.env` sets host ports, the two scripts live at the root
  ([ADR-0031](decisions/ADR-0031-compose-stack-and-ports.md)).

## Key flows
Five implemented: forgotten password (`POST /auth/password/restore`, then `/reset`, task 7.6: unauthenticated; restore stores the sha256 of a random token valid 30 minutes and queues the email job after the commit, the worker logs it in `local`, `development` and `test`; reset checks the token with no pooled connection held, then one conditional UPDATE stores the new hash and ends every session; an OTP-only account sets its first password this way), password change (`POST /auth/password/change`, task 7.5: Bearer, the current password checked with no pooled connection held, then one conditional UPDATE stores the new hash and ends every session, reset token and sign-in code; 204, the account signs in again), refresh and sign-out (`POST /auth/refresh`, `/auth/sign-out`, task 7.4: the refresh token is single use, swapped by one UPDATE conditional on the hash that was checked; sign-out clears the hash and the sign-in code, 204, idempotent), OTP sign-in (`POST /auth/otp/request`, then `/auth/otp/verify`, tasks 7.1 and 7.2) and password sign-up and sign-in (`POST /auth/sign-up`, `/auth/sign-in`, task 7.3; both unauthenticated, one Argon2 hash or check each with no pooled connection held, every sign-in failure one 401 `INVALID_CREDENTIALS`). The flow still to port (file upload) are
described in the Node base's `docs/ARCHITECTURE.md`; the REST versions are specified by tasks 7.1–7.6 and 8.2–8.3 of the scope doc.
