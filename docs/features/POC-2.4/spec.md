# POC-2.4 — Alembic and the `0001_init` revision

Scope-doc row 2.4 (4 h). Depends on 2.2 and 2.3 (both merged, PRs #8 and #9). The ticket text: "Alembic (async env) and revision `0001_init` = final state of
the four Prisma migrations (`CREATE EXTENSION postgis`, enums, tables, FKs, indexes); rollback note in the docstring. `AccountProfile` has no `SSN` or `is18YearOld`
column (ADR-0015)." Files in the row: `api/alembic/**` (stale: ADR-0010 and ADR-0011 drop `api/`). Acceptance in the doc: "`alembic upgrade head` on an empty DB
works; `alembic check` shows no diff". Reference: the Node DDL in `../poc-base/api/prisma/migrations/` (init, `kan_6_postgres_file_storage`, `kan_6_drop_file_status`,
`kan_12_password_auth`) and ADR-0004 ("Revision `0001_init` is the final state of the four Prisma migrations").

## Problem
The ten models exist (2.2, 2.3; nine after ADR-0018) but no database can be built from them: `Base.metadata.create_all` is a test helper, not a deployable path. Tasks 2.5 (parity diff against a
Prisma-migrated database), 3.1 (test database from migrations), 5.1 (seeds) and 11.1 (container) need a versioned, reviewable schema history that starts from the Node base's final state.

## Goal / business value
Goal 1 (scaffolding): a fork runs one command to get the whole schema. Goal 3 (test base): the real-database tests will build their database from this revision (3.1). Rule P6 holds:
nothing in the revision issues a `DELETE`; `DROP TABLE` in the downgrade is a schema change.

## Scope
- in: the `alembic` runtime dependency; `alembic.ini` and an async `migrations/` environment that reads the URL from `Settings.database_url`; hand-written revision `0001_init`
  (extension, the two enums, nine tables with keys, foreign keys with their actions, twelve indexes, a working downgrade, rollback note in the docstring); an `include_object` hook for PostGIS's
  own table; unit tests (offline SQL, no database) and a real-Postgres test in a database of its own; the command map, runbook, architecture and protected-path updates.
- **out (explicit):** the `pg_dump` parity diff against the Prisma schema (2.5); building the test database from the revision (3.1); seeds (5.1); a Dockerfile or any container step (11.1);
  CI changes (rule T4); auto-running migrations at app start-up; any further revision; `SSN` / `is18YearOld` (ADR-0015); Redis.

## Acceptance criteria
- [x] AC1 Given an empty PostGIS database and `DATABASE_URL` pointing at it, when `alembic upgrade head` runs (here through `command.upgrade` on the real env), then it ends at revision `0001_init`, the `postgis` extension exists, and the nine tables, two enum types, twelve indexes and nine foreign keys exist.
- [x] AC2 Given that database, when `alembic check` runs (`command.check`), then it reports no diff between the revision and `Base.metadata`, with type and server-default comparison on; and given a dropped index, it fails with `AutogenerateDiffsDetected` (the check is not vacuous).
- [x] AC3 Given a migrated database, when `alembic downgrade base` runs, then no application table, enum type or index remains (the extension and PostGIS's own objects may), `alembic_version` is empty, and `upgrade head` works again.
- [x] AC4 Given no `DATABASE_URL`, then `alembic upgrade head` fails with a `FAILED:` message naming the variable, with no traceback and no connection attempt; the URL is never written in `alembic.ini` or a revision.
- [x] AC5 Given `alembic upgrade head --sql` (offline), then the rendered SQL names exactly the tables, enums, indexes and foreign keys that `Base.metadata` holds (derived from the metadata, not hard-coded) and no `SSN` or `is18YearOld`.
- [x] AC6 `uv run mypy` (strict, now including `migrations/`), ruff and both test suites pass; `uv.lock` was changed by `uv` only.
- [x] AC7 Docs match: ADR-0017, command map in `CLAUDE.md`, RUNBOOK, ARCHITECTURE, `.env.example`, the structure rule, and `migrations/versions/` is an ask-first path.

## Changed after the plan was approved
- On the human's instruction ("while all migrations are controlled by Alembic we do not need the `Migration` model"), the Node `Migration` table is not mapped and `0001_init` has nine tables, not ten: removed from `app/models/system.py`, the revision, the tests and the docs, and recorded in [ADR-0018](../../decisions/ADR-0018-drop-migration-table.md). It was done on this branch, not in a new PR, because `0001_init` was still unmerged and the change edits it. A database that ran the earlier `0001_init` still has the table: downgrade with the old revision first, or drop it by hand.

## Built differently from the plan
- AC7 is met except `.env.example`: its `DATABASE_URL` comment still says "Task 2.1". The plugin hook `guard-protected-paths` (rule C3) blocks edits to that file although `protected-paths.md` exempts it; left for a human.
- The R2 spike (AccountRole, Account, the enum and the `DESC` index, then `command.check`) ran through the R3 fixture as a temporary test: an ad-hoc script containing `DROP DATABASE` was blocked by the destructive-SQL hook (rule C4). The spike was clean, so the full revision followed; the temporary test was replaced by the real ones.
- The enum types are created by `op.execute("CREATE TYPE ...")`, not `ENUM.create(op.get_bind())`: offline mode (`--sql`) has no bind. Each table's indexes are created right after the table, not all at the end; the set is the same.
- `env.py` passes `disable_existing_loggers=False` to `fileConfig` (the template's default would silence the loggers of the process that runs a command, a test run for one), and builds its engine with `app.core.db.create_engine` unchanged, default pool, disposed after use.
- `.claude/rules/project-structure.md` rule 1 also gained `system.py` (stale since 2.3, rule E2), beside the `migrations/` tree line and rule 9.
- Mutation checks, not committed: dropping an index makes `check` fail with exactly one `add_index`; changing `File.size`'s default in the revision makes it fail with `modify_default`.

## Edge cases
| Case | Expected behaviour | Decided by |
|------|--------------------|-----------|
| PostGIS creates `spatial_ref_sys` in `public` | `include_object` skips only that table; any other table the metadata lacks still shows up in `check` | Q4 |
| `CREATE EXTENSION postgis` needs a superuser and the extension files | the revision runs it with `IF NOT EXISTS`; a role without the right fails with Postgres's own message, stated in the RUNBOOK | scope row |
| The downgrade and the extension | tables and enums are dropped, the extension is left (objects in the database may depend on it); the docstring says so | Q3 |
| `asyncio.run` inside the env while a test is already in an event loop | the real-Postgres test calls `command.*` in a worker thread (`asyncio.to_thread`) | Alembic async cookbook |
| An applied revision is edited later | forbidden: `migrations/versions/**` becomes ask-first so a change is a new revision | Q5 |
| Column order of the revision versus the Node tables | the revision follows the Node physical order (the later migrations applied, `SSN` / `is18YearOld` removed), because `pg_dump` prints columns in that order and ADR-0015 expects task 2.5's diff to differ in exactly two columns. `alembic check` does not compare order; a unit test pins it for all nine tables. The models' declaration order may differ | ADR-0015, review finding |
